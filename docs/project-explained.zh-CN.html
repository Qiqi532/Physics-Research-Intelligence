Physics Research Intelligence：项目功能、技术实现与演进说明

面向项目创建者与非技术读者｜核对日期：2026-11-04｜依据：当前工作区代码、测试和项目文档。

阅读建议：先看第 1、2、7、9 章，理解定位与全貌；需要与开发者讨论时，再看实现细节和路线图。

本文的“已实现”表示仓库中存在相应实现和可核对的调用路径，不表示已验证你电脑上所有服务正在运行。本次没有连接个人数据库、调用真实模型、下载论文或重新进行人工质量评审。未来方案均注明属于“仓库规划”还是“工程建议”。

1. 先回答你最关心的三个问题

1.1 这个项目现在到底是什么？

它是一个面向物理研究者、本地优先、单用户的 AI 论文情报与阅读管理工作台。

它把原本分散的工作串起来：从公开学术接口收集论文信息，初步判断哪些值得看，生成基于摘要的中文结构化解读，再按你的兴趣和阅读状态组织起来。

可以把它理解为一个由三部分组成的工作台：

  • 论文情报员：收集、整理、去重和初步筛选论文。
  • 摘要阅读助理：说明研究内容、可能的创新和局限，并披露信息不足。
  • 个人阅读管理员：管理兴趣、收藏、稍后读和阅读进度。

目前最合适的阶段描述是“可本地试运行的单用户 MVP”。MVP 是最小可用产品：核心链路已成形，但质量验证、长期自动运行、全文阅读和部署能力还在完善。

1.2 它现在算不算 RAG 个人助手？

从产品愿景看，它可以演进成科研 RAG 个人助手；从当前代码看，还没有实现通常所说的知识库 RAG 问答链路。

现在的核心模式是：选定一篇论文，把它的标题和摘要直接交给模型，要求生成结构化解读。尚未建立“根据用户问题，从个人论文库检索相关段落，再用这些段落生成带引用答案”的系统。

因此，现阶段对外建议称为“AI 科研论文助手”或“物理论文情报工作台”。可以补充“未来计划加入基于个人收藏库的 RAG 问答”，把目标与现状说清楚。

1.3 应该怎样介绍它？

一句话版本：

我做了一个面向物理研究者的个人论文情报工作台，它能从公开来源整理文献、生成可追溯的中文摘要解读，并根据兴趣和阅读状态帮助我决定先读什么。

介绍时先讲“替你完成哪一段研究工作”，再讲 AI 和技术。RAG 是实现方法之一，不必作为项目最前面的标签。第 9 章提供不同对象适用的完整讲稿。

这是一套 Web 与 Worker 分工的模块化应用，还不需要把每个包理解成独立微服务。现在增加更多服务会增加个人部署负担，现有边界已经能支持下一阶段演进。

3.3 “本地优先”不等于完全离线

论文数据库、个人阅读状态、模型连接配置主要在本机环境中管理。但采集需要访问学术接口，真实 AI 解读需要把公开标题和摘要发送到所配置的模型端点。

所以准确说法是“本地保存与管理个人工作流，按需调用外部数据和模型服务”。当前不能宣传成“所有内容完全不出本机”或“无需联网即可完成全部功能”。

4. 现有功能逐项拆解

4.1 公开论文采集：把分散来源变成统一论文记录

你得到什么： 不必逐个网站复制论文标题、摘要和链接，后台可以从多个公开接口获取信息。

输入与输出： 输入是来源、日期窗口、查询和分页位置；输出是统一论文记录，通常包含标题、摘要、DOI、期刊、作者、日期、原文链接与访问状态。来源未提供的字段可以为空。

实现路径： 来源连接器发起 HTTP 请求并解析各自格式，再交给采集任务持久化。SourceSyncState 记录来源同步状态；有分页、限流及有界重试处理，避免一次失败就丢失全部同步进度。

Crossref 侧重出版元数据；OpenAlex 提供统一学术记录及部分开放访问信息；arXiv 提供预印本记录。它们的连接器存在，不代表每次日常运行都完整覆盖三方，也不代表题录一定含摘要。

重要限制： 当前日常流程包含期刊白名单。缺少期刊信息、尚未正式发表或不在白名单的预印本，即使被采集，也可能进不了后续筛选。因此“有 arXiv 连接器”和“日常全面追踪 arXiv”是两件事。

后续路径： 先统计每个来源的采集量、缺摘要率和重复率，再决定是否新增来源或单设预印本通道；不要只以来源数量衡量覆盖质量。这是工程建议。

代码入口： 来源连接器、采集任务、来源进度。

4.2 事实层与去重：同一篇论文尽量只维护一份主档案

你得到什么： 同一篇论文出现在不同数据源时，可以聚合来源，同时保留来源信息，不必把多个副本当成不同论文。

实现路径： Paper 存主档案，PaperSource 存不同来源的记录。优先使用规范化 DOI；来源名称与来源记录 ID 也有唯一性约束。无可靠身份信息时采取保守处理，相似标题不直接等于同一论文。

为什么要分层： 来源给出的标题、摘要属于事实输入；模型生成的“创新点”属于解释。它们分开存储，模型不能用自己的推断覆盖原始论文事实。未来更换模型时，可以重做解读而保留来源链。

重要限制： “公开可访问”“有开放状态”“许可允许外部模型处理全文”需要分别判断；现有访问状态并不是完整的全文授权系统。另外，无 DOI 论文可以入库，但当前详情和状态操作主要围绕 DOI 路由，网页操作能力存在缺口。

后续路径： 保留 DOI 作为学术标识，逐步使用内部 paperId 支撑页面和操作；为疑似重复增加人工确认入口。前者可解决无 DOI 文献的收藏和阅读管理问题。这是工程建议。

代码入口： 论文身份规则、论文仓储、数据库结构。

4.3 期刊规则与 AI 批量筛选：先缩小候选池

你得到什么： 每天采集的信息先经过一轮筛选，把模型解读资源集中在较值得关注的论文上。

当前主流程： 公开元数据入库后，先按期刊白名单做确定性过滤，再分批调用 AI 筛选。当前每批最多 15 篇，筛选 Prompt 使用标题、期刊和摘要前 200 个字符等信息，要求模型返回论文 ID、方向、分数、理由和是否选中。

实现路径： 校验输出是否覆盖该批次、是否存在未知或重复论文 ID，以及分数和方向是否合法；写入 PaperScreening。筛选也会把方向和分数写入 PaperClassification，供推荐模块继续使用。

重要限制： 摘要截断有助于控制输入量，也可能漏掉摘要后半部分的关键信息。日常筛选写入的是一个主要方向，不能据此推断已经完成了细致的多标签交叉学科识别。期刊白名单也会引入来源选择偏好。

后续路径： 用人工评估比较“200 字符、较长摘要、完整摘要”的漏选情况；把“论文是否值得看”和“属于哪些方向”分开验证。未获得证据前，不把模型筛选分数解释成科研质量的客观评分。这是工程建议。

代码入口： 期刊规则、批量筛选任务、筛选 Prompt。

4.4 物理方向分类与兴趣设置：明确你关心什么

你得到什么： 系统可以按物理方向组织论文，你可以显式调整关注程度。

实现路径： 预定义 9 类标签，包括原子分子光学、凝聚态材料、高能粒子、核物理、天体物理、统计计算、等离子体、生物物理和交叉物理。独立分类任务能生成标签、相关性与理由；兴趣设置把各标签的 0–2 权重保存为 UserInterest。

当前每日主流程主要使用上一节的批量筛选结果建立方向标签，独立分类实现仍存在并用于相关试验等场景。不能把早期“逐篇独立分类”的设计，直接当成目前日常运行方式。

重要限制： 兴趣是显式规则输入，尚未实现从点击和阅读历史训练个人偏好模型。把一个方向设为高权重会影响排序，不等于系统已经理解你的具体课题、设备条件或研究假设。

后续路径： 如果希望推荐更贴近课题，先增加可解释的研究主题或关键词配置，并为“非常相关但标签较宽”的论文建立测试案例；再评估是否需要语义表示。这是工程建议。

代码入口： 标签定义、分类任务、兴趣界面、兴趣仓储。

4.5 中文结构化解读：把摘要整理成可核对的阅读材料

你得到什么： 对一篇论文看到统一格式的中文概述、创新点、证据、局限与不确定性，减少第一轮阅读成本。

输入与输出： 当前 PaperAiInput 主要接受标题、摘要、期刊和发表日期。解读 Prompt 明确使用 abstract_only；输出需满足既定 JSON 结构，之后单独保存在 PaperInterpretation，记录 provider、model 与 Prompt 版本。

实现路径： 构建有限输入 → 选择模型路由 → 调用供应商 → 解析并校验结构 → 保存解读及审计 → 页面展示。缺摘要或依据不足时应明确披露，不应补造设备、参数、实验步骤或全文结论。

重要限制： 当前是摘要级解读，不是全文精读。数据类型里存在开放内容相关枚举，并不表示已接入全文内容。页面把 direct / inferred / uncertain 映射成“高 / 中 / 低置信度”，它只是证据等级标签，不是经校准的概率，也不是独立事实核查结论。

目前引用字段主要经过结构校验，尚无逐条自动确认“引用原文确实支持该结论”的验证器。因此“可追溯”表示便于回看来源，不能等同于“所有结论已经证实正确”。

后续路径： 先完成人工复核、建立失败样例和模型基线，再扩展输入到可授权的全文证据；不要只通过加长 Prompt 来宣称质量提升。质量评审属于现有规划，证据自动核验是工程建议。

代码入口： AI 输入契约、解读 Prompt、输出校验、解读任务、展示转换。

4.6 论文详情与手动解读：让用户控制处理时机

你得到什么： 详情页展示公开摘要、来源、原文链接、方向标签和已生成的解读；Today 卡片可以手动请求某篇论文的 AI 解读。

实现路径： 详情页由服务端查询论文及关联数据。手动按钮调用 POST /api/papers/[doi]/interpret，Web 服务检查论文和已有运行，调用模型并写结果及审计，再返回成功、已完成、处理中或失败状态。

重要限制： 此入口直接在 Web 请求内运行，并没有把任务交给 BullMQ。模型很慢时，请求时长和用户刷新会成为体验问题；已有“处理中”提示也不等于完整的后台进度轮询功能。

后续路径： 把手动解读提交到持久队列，立即返回任务标识；页面查询状态并支持重新进入、取消和显式重试。复用现有 AI 任务逻辑，避免做两套解读规则。这是工程建议。

代码入口： 论文详情页、卡片交互、手动解读服务。

4.7 Today 推荐与跨方向信号：帮助决定先看什么

你得到什么： 一份按规则排序的候选论文列表、最多三条推荐理由、交叉方向统计，以及稍后读/正在读队列。

实现路径： Today 查询最近 30 天发表的论文，并保留稍后读或正在读的论文作为候选，默认查询上限为 500。查询分类、兴趣和个人状态后，用确定性规则评分。

评分项当前规则应如何理解
兴趣匹配40 × 最大值（标签相关度 × 兴趣权重 / 2）强调你显式关注的方向
分类相关度30 × 最高标签相关度强调分类判断较强的论文
时效20 分在 30 天内线性衰减至 0适度偏重新论文
交叉方向10 × 最高交叉标签相关度给跨方向发现一些空间
阅读与反馈稍后读 +10，正在读 +8，完成 −20，跳过 −35；LIKE +8，DISLIKE −25调整同一篇论文的优先级

最后 Today 还会把“已有解读”的论文排到前面，再按分数排序。因此最终顺序不能只用总分解释。这里也没有训练推荐模型或协同过滤系统。

必须区分的两条链路： 每日 Worker 的确有“尽量选 10–15 篇、限制单方向数量”的算法；但 Today 当前没有按本次筛选的 selected / batchId / deliveredAt 过滤，而是重新查询候选池。因此它不是严格的每日选中清单，列表可能超过 15 篇，也可能包含其他候选论文。

统计口径： 界面“今日新论文”目前对应上海时区昨日入库的候选论文，且受候选池范围影响，不是全库今日新增总数。跨方向信号统计则基于当前推荐列表里的交叉标签，不代表系统已证明存在新的科研关联。

后续路径： 优先统一“今日精选”和“全部近期候选”的定义；用持久化批次连接每日选择与页面；同步改正统计标签和范围。这是工程建议，也是现阶段较值得先补的小闭环。

代码入口： Today 查询、推荐与每日选择算法、推荐理由、Today 页面。

4.8 收藏、阅读进度与保留期：建立个人论文工作流

你得到什么： 可以收藏论文，设置稍后读、正在阅读、已完成或不感兴趣；收藏库按收藏时间组织。

实现路径： UserPaperState 将阅读状态、反馈和 isFavorite 分开保存。收藏是一项独立属性，所以一篇论文可以同时“已收藏”和“正在阅读”。收藏库主要查询 isFavorite=true 的论文。

普通论文清理按 createdAt 即入库时间计算。超过默认 30 天且没有收藏保护的论文会被清理，并按数据库关系清理相关记录。收藏长期保留是应用清理规则，不代替备份。

重要限制： “稍后读”或“正在读”本身并不豁免清理。想长期保存的论文需要收藏。取消收藏不会立刻删除，但之后如果已过保留期，可能在清理时删除。

后续路径： 在界面明确说明保留规则，清理前展示可理解的影响范围；未来增加 PDF 后，要让数据库记录、文件和索引一起遵守删除规则。前者是工程建议，后者与已有本地库规划一致。

代码入口： 阅读和收藏控件、收藏库页面、收藏查询与清理。

4.9 模型管理与主备路由：减少对单一供应商的依赖

你得到什么： 可以创建多个命名连接，设置供应商、模型和 Base URL，执行连通测试与合成论文测试，并分别配置分类、解读的主模型和备用模型。

实现路径： 统一 Provider 契约封装不同服务。仓库有 OpenAI、DeepSeek、Gemini、Qwen、GLM、Kimi、混元及通用 OpenAI-compatible 适配实现。模型名由连接配置决定；适配器存在不代表所有供应商当前所有模型都已真实验证。

批量筛选复用分类侧模型能力和路由。主模型遇到网络错误、超时、限流或上游 5xx 时，才允许一次备用尝试。认证错误、输出结构不合格或模型表达不确定，不会因此无条件换模型。

密钥保存： API Key 用 AES-256-GCM 加密保存到本地数据库，主密钥独立于数据库、默认在仓库外保存。浏览器获取已有连接时不应收到已保存的明文 Key。模型设置变更还有同源、JSON 类型和请求大小等检查。

重要限制： 加密存储不能替代操作系统权限和主密钥备份；无登录也不能被同源检查替代。金额计算、价格配置与预算阻断已按项目既有决策移除，当前保留供应商实际返回的 Token 和耗时等审计信息，账单与余额以供应商平台为准。旧设计中的费用能力不应再当成当前功能或默认待办。

后续路径： 对实际要用的连接建立测试记录，区分“网络连通”“结构契约通过”和“真实论文质量达标”；模型或端点变化后重复相应检查。这是工程建议。

代码入口： 适配器工厂、路由器、密钥加密、管理服务、请求保护。

4.10 审计、缓存与幂等：让 AI 工作可以追踪和重跑

你得到什么： 能记录处理了什么论文、使用哪个模型和 Prompt、是否成功、耗时和 Token 用量，并避免某些重复执行。

实现路径： AiRun 表记录逻辑任务，AiRunAttempt 记录实际主备调用尝试；成功结果与失败错误分别记录。幂等的意思是：同一项工作重复请求时，尽量复用结果而非无限创建副本。

重要限制： 当前解读幂等键主要包含论文 ID、任务类型、主模型名称和 Prompt 版本。虽然另存 inputHash，它没有进入该唯一键。因此摘要更新后，同模型同 Prompt 可能仍复用旧成功结果；筛选批次的哈希也不是对摘要和兴趣等全部语义输入的完整版本标识。

这意味着系统已有去重与审计基础，但还不是完善的“输入变化自动失效、所有阶段可靠恢复”体系。也不能仅因记录了 inputHash 就认为输入更新一定触发重算。

后续路径： 明确定义内容、Prompt、模型、配置版本变化如何使结果失效，再统一 Web 和 Worker 的任务身份；新增测试证明更新摘要或切换配置时的行为。这是工程建议。

代码入口： 通用 AI 任务、AI 结果与审计仓储、数据库结构。

4.11 每日流水线与调度：已有闹钟，可靠性闭环仍需补齐

你得到什么： 后台已经能够按时区配置注册每日任务，依次执行采集、筛选、选择、解读、Today 准备、投递标记和清理。代码默认时间为上海时区 00:00，时间和时区均可配置；默认自动调度关闭。

实现路径： BullMQ 在 Redis 中注册稳定的调度任务；Worker 并发为 1。每日任务最多尝试 2 次，指数退避起点为 30 秒。它不是靠页面保持打开，也不是应用里简单的 setInterval。

当前默认滚动采集窗口为 30 天，投递去重窗口默认跟随采集窗口。选取算法尽量达到 10–15 篇，并对单方向做数量限制；候选不足时不会自动凭空补齐。论文级近期投递记录用来避免重复选入，只有 Today 准备之后才写投递标记。

每日选择与 Today 评分也并非完全相同：每日选择目前把阅读状态固定为未读、反馈固定为无反馈；筛选方向在该阶段没有启用交叉标签加分。它主要使用兴趣、筛选分数、时间和方向数量限制，不能宣传为已全面结合个人阅读反馈的每日精选。同一日期窗口重跑，还可能因近期投递抑制而选出下一批论文，尚无不可变的日报快照。

“投递”的含义： 这里是内部状态记录，没有实现邮件或消息平台推送；本轮选中的论文即使解读失败，也可能被写上投递时间，所以“已投递”不等于“已成功解读”。

重要限制： 队列状态不是数据库里的权威每日运行总账；单进程并发为 1 也不等于两个 Worker 互斥。目前缺少运行账本、跨进程租约、心跳、中断恢复与主动告警。因此“有定时功能”可以说，“已达到稳定无人值守”还不能说。

后续路径： 按第 6.3 节先补账本、锁和恢复，再做连续影子运行。不要仅把开关改为 true 就当成完成自动化。

代码入口： 调度器、Worker 运行时、每日阶段编排、实际处理器。

4.12 测试、健康检查与试验语料：工程检查与科研质量分开看

你得到什么： 仓库有领域规则、数据源、模型适配、数据库、Worker、API、组件和浏览器端到端测试。健康端点可以检查服务存活及数据库、Redis、Worker、队列等依赖状态。

实现路径： Vitest 检查模块和契约；数据库测试使用独立测试环境；Playwright 检查桌面与移动浏览器流程。Mock Provider 用固定的本地行为代替真实模型，便于重复验证且避免自动测试访问真实服务。

review-corpus、journal-corpus 提供评估材料与专用下载/导入工具。已有 PDF 文件或下载脚本，只能证明评估资料管理存在；导入流程主要写公开元数据和摘要，不能证明应用已经能解析 PDF 并问答。

质量进度： 仓库记录了三篇 Kimi 摘要试运行，以及 30 篇 AI 输出和第一轮初评。当前不能把第二位人工复核写成已完成。该次 trial 没有完整产出推荐筛选和跨方向信号证据，D5 推荐理由、D6 跨方向发现价值应按评审范围标 N/A，不能当成通过。

重要限制： 测试通过能证明特定代码行为符合预期，不能证明模型对每篇科学论文都理解正确。健康检查正常，也不能证明每日精选和解读质量达标。

后续路径： 将软件测试与人工科学质量基线并行维护，保留原始输出、评审分歧和失败样本。自动化运行状态的评估还需补充完整流水线证据。

证据入口： 测试目录、健康检查、质量标准、30 篇评审材料、Kimi 试运行报告。

5. 数据怎样保存：这是理解项目可维护性的关键

数据表或模型保存什么为什么需要单独保存
Paper论文主档案提供统一身份，不为每个来源重复建立整套个人状态
PaperSource来源记录、链接、抓取时间、许可线索等能回看信息来自哪里，保留来源差异
PhysicsTag / PaperClassification主题标签、相关度、分类理由和版本组织论文并支持推荐解释
PaperScreening批量筛选分数、方向、批次、入选与投递状态区分收集到的论文和筛选结果
PaperInterpretationAI 生成的结构化解读及版本与来源事实隔离，便于重做和比较
UserInterest个人方向权重推荐偏好可见、可调整
UserPaperState阅读状态、反馈、收藏和预留笔记个人操作不污染公共论文事实
AiRun / AiRunAttempt模型任务、实际尝试、Token、耗时、错误追踪成功和失败，支持幂等处理
SourceSyncState采集进度及来源运行状态支持后续同步和排错
AiConnectionProfile / AiRuntimeRouting加密连接与任务路由切换模型无需到处改代码

当前没有完整的 Document / Chunk / Embedding / Conversation / Message 一类全文与对话数据模型。这些名称只是解释未来需要哪些职责，不是声称仓库已存在这些表，也不是必须照此命名的新 API。

持久数据库保存应恢复的业务事实；Redis 队列保存可重建的运行状态；未来 PDF 文件和索引也要定义备份关系。恢复数据库、恢复主密钥、恢复论文文件是不同工作，不能只复制仓库就认为已完成备份。

6. 未来功能：目标、技术路径与验收标准

6.1 先分清已有规划与新增建议

仓库现有主线是：质量基线 → 每日流程可靠性 → 本地 PDF 资产 → 单篇阅读助手 → 收藏库 RAG。

早期路线图的阶段名称为 9A、9B、10、11。9A 中的独立收藏、普通论文清理、每日选择和收藏页已有实现，不能再整阶段列为“未开始”；但 Today 与每日选中集的衔接仍有缺口。9B、10、11 尚无完整实现。

早期文档中“implementation has not started”、金额预算等表述已与现有代码不同。本文以代码和较新的状态说明为准，不将旧计划的复选框直接当成完成情况。

下列顺序是综合现有规划后的工程建议，没有承诺工期，也没有在本次修改中实现这些功能。

6.2 阶段 A：完成质量基线，并统一现有产品口径

来源： 人工质量基线属于仓库规划；口径与任务身份修补属于本次工程建议。

目标： 先知道现有摘要解读哪里可信、哪里会误导，并让页面行为与介绍一致。

实现路径：

  1. 完成 30 篇人工复核，分别记录事实忠实度、概述、创新依据、局限披露，保留与第一轮评审的分歧。
  2. 给缺乏真实流水线证据的 D5/D6 保留 N/A；另跑受控全流程样本，专门评估推荐与跨方向价值。
  3. 将每日选中批次与 Today 页面接通，或者明确分成“每日精选”和“近期候选”；统一新论文的时间和统计范围。
  4. 让输入变化、模型配置和 Prompt 版本与缓存失效规则一致；解决无 DOI 论文的详情与状态操作。
  5. 把摘要级证据等级讲清楚；保留错误和不确定性，不用高置信标签掩盖信息不足。

验收： 每个宣传中的功能都能演示；样本有原始输入、模型版本、人工裁定与失败案例；同一批次的精选数量和页面结果一致；更新摘要后的重算行为可预期。不能用一个“总准确率”概括所有能力。

依赖与难点： 主要是评审标准和现有链路的一致性，技术成本小于新增全文系统，却会直接影响后续可信度。

6.3 阶段 B：把每日任务变成可恢复的自动工作流

来源： 每日自动化规范。

目标： 电脑重启、来源故障、模型超时后，仍能知道今天做到了哪一步，并安全继续。

实现路径：

  1. 在 PostgreSQL 建立每日运行账本，按日期窗口唯一，保存状态、阶段、数量、耗时、尝试次数与稳定错误码。
  2. 用数据库原子操作获取租约，附 owner token、过期时间和心跳，防止两个进程同时处理同一窗口。
  3. 按采集、筛选、解读、Today、清理记录断点；恢复时复用已完成且输入未变的工作。
  4. 区分 SUCCEEDED / PARTIAL / FAILED。部分论文失败可以保留其他成果，但状态必须如实显示。
  5. 增加本机状态查询、重试、恢复和跳过入口；超过次数后保留失败记录，避免无穷重试。
  6. 提供告警适配边界。具体外部渠道需单独选择；本次不新增消息、邮件或其他网络调用。

验收： 同窗口重复执行不重复出结果；双 Worker 只有一个持有租约；在每阶段后模拟退出，重启后可收敛到唯一终态；单来源失败和全部来源失败能区分；至少连续 3 天影子运行有完整证据，再按原有门禁决定是否开启定时。

难点： 幂等键、数据库事务、租约过期和旧进程延迟写入之间的配合。单纯增加重试次数不能解决这些问题。

6.4 阶段 C：本地 PDF 资产管理与合规获取

来源： 本地库路线图 Phase 9B。

目标： 收藏论文可以关联真实 PDF，并明确文件来自哪里、是否存在、允许怎样使用。

实现路径： 为文件建立资产记录，包括论文身份、来源、许可判断、SHA-256、大小与本地可用状态。文件放在被 Git 忽略的个人目录，Web 返回不暴露绝对路径的资产标识。

自动下载采用明确允许的来源和许可条件，限制大小、类型、重定向与校验结果；“链接能下载”不能自动等于“允许发送给外部模型”。第一版按现有路线图优先做本地 CLI 导入，再评估浏览器上传。

验收： 同文件重复导入不生成多个副本；损坏文件、伪装 PDF 和无许可自动下载会被阻止；数据库和文件可一起备份恢复；取消收藏和论文过期后的文件处理符合明确规则。

难点： 文件身份、许可状态、路径隔离和数据库一致性。这一阶段完成后只是“管好文件”，还没有完成全文理解或 RAG。

6.5 阶段 D：全文解析与可定位证据

来源： 单篇助手和 RAG 的必要前置能力；以下拆解为工程建议。

目标： 将 PDF 变成能检索、能定位、能核对的文本，而不是一段失去出处的长字符串。

实现路径： 在受限解析进程中按文件哈希处理；先支持有文本层的数字 PDF，提取章节、段落与页码，记录解析器版本和质量状态。保留稳定段落标识及来源坐标；对双栏、页眉页脚、连字符、公式、表格和参考文献分别处理。扫描件再引入 OCR，不把它混作普通文本解析成功。

解析结果与原始文件分开保存。修改解析器可以重建文本和下游索引，不需要重新改变论文事实。只对明确允许模型使用的内容构建后续证据包。

验收： 随机选取重要段落能跳回正确页或位置；双栏顺序不会串行；公式和表格丢失会有提示；解析失败可以重试、升级和重建；不把解析错误当成科学结论交给模型。

难点： 物理论文中的公式、图表和补充材料。第一版应明确支持范围，先保证文本证据可靠，再扩展图表理解。

6.6 阶段 E：单篇论文阅读助手

来源： 本地库路线图 Phase 10。

目标： 针对一篇论文解释术语、总结章节、回答具体问题，并核对某个结论是否有原文支持。

实现路径： 页面选择论文和允许使用的内容；后端构建大小受限的证据包，附段落标识；模型返回答案、引用和不确定性。单篇短文可先使用受控全文上下文，长文再做篇内检索；是否采用检索要由内容长度和评估决定。

增加会话、消息、取消、删除、稳定错误和任务状态。Provider 只接受明确的证据数据，不直接获得任意本地文件或数据库访问权限。手动导入或受限内容向外发送前必须具有可见的资产级授权状态。

验收： 每个关键回答能定位来源；原文没有答案时明确说不足；不会把一篇论文的观点扩张为整个领域共识；删除会话与更改授权会影响后续使用；超时和取消不会导致无限重复调用。

难点： “回答看起来合理”与“原文确实支持”不同。单篇对话也不自动等于跨论文 RAG；把全文一次塞给模型，是上下文问答的一种实现。

6.7 阶段 F：收藏库检索与跨论文 RAG

来源： 本地库路线图 Phase 11。

目标： 问“我的收藏里，哪些论文讨论了某种噪声抑制方法？它们的条件有何不同？”，系统找到证据后做跨论文比较。

索引阶段： 只选择收藏且允许模型处理的内容 → 按章节语义切块 → 为片段保存论文 ID、页码/段落、内容哈希与版本 → 生成 embedding → 保存检索索引。

Embedding 是文本的数值表示，用来比较语义接近程度；它不是模型已经证明两段内容在科学意义上等价。现有聊天供应商适配不等于拥有 embedding 能力，必须单独定义和验证。

回答阶段： 用户问题 → 选择授权范围和元数据条件 → 检索相关片段 → 必要时重排 → 把有限证据交给生成模型 → 返回分论文、分主张的答案和定位引用。证据冲突时并列呈现，不能强行合并。

仓库路线图对个人规模的初版偏向：把向量先保存在 PostgreSQL，并在应用侧做有界相似度计算，以减少新服务；测到规模或延迟瓶颈后，再评估扩展或专门检索服务。这是已有路线图的取舍，并非已经安装某个向量数据库。

验收： 预先建立带标准证据段落的问题集，分别测检索召回、引用正确率、无依据主张率、延迟和调用量；删除收藏、文件或论文后，相关片段会删除或失效；换分块方式或 embedding 模型能安全重建全库。

难点： 物理符号、缩写、同名概念和实验条件差异会影响检索。可以在评估后结合关键词与语义检索；不能只展示几个成功问答就宣称知识库可靠。

6.8 阶段 G：反馈、笔记与个人研究记忆

来源： 早期产品设计已有笔记与反馈意图；以下闭环为工程建议，优先级低于可靠性和全文证据。

目标： 保存你对论文的真实判断，让下一次阅读不必从头开始。

实现路径： 先补完整笔记编辑、保存和删除界面，区分“论文事实”“AI 观点”“我的笔记”；以显式反馈改进排序解释；未来若将个人笔记加入检索，记录作者、时间、隐私和来源类型，避免把个人猜想回答成论文结论。

验收： 收藏、阅读、笔记互不覆盖；用户可以更正和删除个人记忆；推荐能够说明哪些显式偏好发生了作用；未经明确设计和授权，不加入隐式行为采集。

难点： 长期个人记忆需要纠错和删除能力，不能只往数据库无限追加内容。现有阅读反馈调整同一篇论文排序，尚不是全局学习课题兴趣。

6.9 阶段 H：认证、部署与可维护发布

来源： 项目现有限制与自动化部署规范；公开服务不应作为当前默认下一步。

目标： 如果将来要跨设备、给别人使用或公开访问，补齐身份、权限和可靠发布能力。

实现路径： 先决定仍是个人受保护部署，还是多人产品。前者可以在受控访问环境中运行；后者必须设计认证、会话、授权和用户数据隔离，将当前固定 userId=default 改为真实身份上下文。再补请求频率与额度、后台任务权限、资产访问、备份恢复及版本化发布回滚。

验收： 用户 A 不能读取用户 B 的论文、笔记或模型密钥；未登录不能触发付费任务；发布失败可以回到可运行版本；数据库与主密钥及未来文件能够实际恢复，而非只有备份命令。

难点： 多用户会改变数据边界与产品成本。应作为独立需求评估，不是把 Web 监听地址改成公网就完成。

7. RAG、个人助手与 Agent：准确理解技术定位

7.1 RAG 的关键是什么？

RAG 是 Retrieval-Augmented Generation，即检索增强生成：先从外部知识存储取回与当前任务相关的内容，再把这些内容作为生成回答的依据。原始 RAG 论文结合了检索器、外部文档索引与生成模型。Lewis 等，RAG 原始论文

面向本项目，可以用下面的对比理解：

当前摘要解读：
选定论文 → 直接提供该篇标题/摘要 → 模型按模板解读 → 保存结果

未来个人论文库 RAG：
用户提出问题 → 从授权论文库检索相关段落 → 组合证据
           → 模型基于证据回答 → 引用具体论文与原文位置

这里对当前项目的判断来自仓库代码检查，不是外部论文对本项目的评价。

7.2 为什么有数据库、来源链接和 AI 还不够？

数据库负责保存内容，不一定执行与问题有关的证据检索；来源链接负责追溯论文，不一定指向支持某个回答的段落；模型生成摘要，也不一定需要检索个人知识库。

判断 RAG 应看“问题或任务驱动的检索结果是否进入生成上下文”，不能只数数据库、模型和引用链接这几个组件。当前缺少的问题检索、可定位片段和问答闭环，是本项目还不宜称为成熟 RAG 助手的主要原因。

向量数据库不是 RAG 的唯一实现方式。 检索也可以基于关键词、结构化条件或混合机制；反过来，只存了向量、没有用于生成时的证据检索，也没有完成 RAG 产品。这里是一般工程解释，不是要求项目立即引入新服务。

7.3 “个人助手”和“智能体”分别意味着什么？

名称它说明什么当前项目是否适合这样叫
AI 论文助手帮用户完成论文处理和阅读工作适合，但说明目前是摘要级
论文情报工作台收集、筛选、组织、追踪和阅读管理最准确的主定位
个人知识库长期组织个人收藏材料已有收藏元数据基础；全文知识库尚在规划
RAG 科研助手检索个人文献证据，再生成答案作为未来目标；当前不能当成已实现主能力
自主科研 Agent自主规划研究步骤、选择工具并迭代执行当前没有对应闭环，不宜这样宣传

目前是由代码预先定义阶段的工作流。大模型参与筛选和解读，不代表模型在自主制定科研计划。项目的价值完全可以建立在可靠、明确的工作流上，无需用更大的技术标签证明价值。

9. 可以直接使用的项目介绍

9.1 向非技术朋友介绍：30 秒

我在做一个帮助物理研究者管理论文信息的个人工作台。它会从公开来源收集论文，根据我的兴趣做初步筛选，把摘要整理成中文的研究概述、创新点和局限，再让我收藏和管理阅读进度。现在主要解决“每天先看什么、怎样快速判断值不值得读”，下一步会加入全文阅读和个人文献库问答。

9.2 向研究者介绍：约 1 分钟

我的项目叫 Physics Research Intelligence，面向实验 AMO 及相关物理研究方向。它把公开论文来源、AI 摘要解读、显式兴趣推荐和个人阅读状态放在同一个本地工作台。

我比较重视来源与解释的分离：原始题录和摘要保留来源，模型输出单独保存，并记录模型和 Prompt 版本。推荐采用可解释规则，也会考虑阅读状态和跨方向信号。

目前还是单用户 MVP，AI 分析只基于摘要，质量评审和每日自动化可靠性还在完善。长期目标是对授权的个人收藏全文建立证据检索和 RAG 问答，让回答能够回到具体论文段落。

9.3 向工程师介绍：技术版

这是一个 TypeScript/pnpm monorepo。Next.js Web 提供 Today、论文详情、收藏、兴趣与模型设置；Node.js Worker 通过 BullMQ/Redis 编排采集、批量筛选和解读。PostgreSQL/Prisma 保存论文事实、来源、AI 输出、审计和个人状态。

数据源适配和模型 Provider 做了模块分离，模型使用结构化输出及有限主备路由，推荐是确定性规则。目前需要补齐 Today 与筛选批次、输入变更与缓存失效、运行账本和租约恢复；全文资产、解析定位、embedding 与检索生成仍是后续阶段。

9.4 介绍时可以强调什么？

  • 领域明确：围绕物理研究者的论文发现和阅读流程，先从具体需求做起。
  • 工作流完整：把采集、筛选、解读、收藏和阅读状态串起来。
  • 便于核对：事实和 AI 输出分层，记录来源与处理版本。
  • 个人可控：数据本地管理，模型可切换，兴趣规则可调整。
  • 边界诚实：现阶段是摘要级 MVP，全文和 RAG 有明确路线。

9.6 一个适合现场演示的顺序：3–5 分钟

  1. 先讲问题：论文来源分散、摘要阅读耗时、收藏后难持续跟踪。
  2. 展示 Today：解释推荐理由和兴趣设置；明确当前是候选池排序，展示不等于固定每日精选。
  3. 打开论文详情：先看来源摘要，再看 AI 解读，指出证据等级和信息不足。
  4. 演示阅读管理：将论文收藏并标记正在读，再打开收藏库；说明收藏与阅读进度独立。
  5. 展示模型管理概念：只展示公开配置和测试状态，避免在公开演示中展示凭据输入。
  6. 最后讲路线：下一步先可靠运行，再全文证据定位，最后才是跨论文 RAG。

使用已有成功输出进行演示更容易控制时间。若现场触发真实解读，应事先确认模型连接和等待时间；不要把未完成的全文问答画面作为当前功能展示。

10. 非技术项目负责人可以怎样与开发者协作？

后续每个功能都要求交付四样东西：一段用户操作、一条真实数据流、一组关键失败情形、一份可重复的验收结果。

你可以问的问题好的回答应该包含什么
“这个功能的输入是什么？”来自哪个页面、数据库或文件；缺少信息时怎样处理
“它到底保存了什么？”保存的位置、身份、版本；是否包含个人内容或密钥
“如果跑到一半电脑重启？”可查询状态、重试边界和恢复方法
“摘要改了会重新分析吗？”明确的缓存失效规则与测试，而非笼统说有幂等
“怎么知道答案有依据？”原文定位、无依据时的行为与质量评估
“删掉收藏会发生什么？”元数据、PDF、片段、向量和会话分别如何处理
“这是真正做完还是只有页面？”端到端演示、失败态和持久化证据
“有没有额外外部调用？”调用目的、发送内容和触发条件；新增行为由你决定

不需要先掌握所有框架。先能说清“资料从哪里来、AI 看了什么、结果保存在哪里、失败如何恢复、用户如何验证”，就已经能有效管理这个项目。
