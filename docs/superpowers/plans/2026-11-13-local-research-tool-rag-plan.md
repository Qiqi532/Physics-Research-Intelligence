# 本地科研工具与 RAG 助手调整计划

日期：2026-11-13。状态：规划稿，本轮不开发、不启动服务、不调用付费模型。

本文依据当前代码、现有项目文档、指定目录的只读盘点和用户本轮补充。这里的“已有”仅表示存在实现，不代表本机运行或科研质量已验收；新增模块、字段及流程均为建议。

## 1. 建议的定位与价值

将项目从“覆盖广泛物理方向的论文情报与阅读管理平台”，收敛为**配合 Codex 与 Zotero 使用的本地科研工具：每天筛选新论文，并为个人文献库提供可定位的证据检索**。

分工如下：

| 工具 | 主要职责 |
|---|---|
| Zotero | 正式题录、收藏分类、附件、批注、引用与参考文献管理 |
| Codex | 临时研究任务、代码、资料整理和按需深度分析 |
| 本项目 | 定期采集、增量去重、稳定研究画像、推荐历史、全文索引、证据定位与运行记录 |

项目的价值是持续执行、保存状态和复现结果。它不必重复实现 Zotero，也不必成为新的通用 Agent 或聊天入口。即使暂时不打开网页，后台仍能产生可阅读的本地日报，索引也可以复用。

第一版只保留三个主要入口：**今日推荐、检索与问答、设置与运行状态**。沿用现有页面框架；原有收藏和阅读状态先兼容保留，停止扩建另一套文献管理系统。

投入判断：先交付可靠日报，再交付全文检索。连续观察约两周，如果它不能减少重复找论文、漏看新论文和定位证据的时间，就保留命令行与日报输出，暂停网页及高级问答扩展。没有人工相关性反馈时，这一观察只能证明流程能否持续提供材料，不能证明推荐已经符合个人偏好。

## 2. 已确认需求与尚未确定的条件

已确认：

- 保留基础框架，尽可能小型化；只在本地部署，不建设公网服务器。
- 现有工作流为 Codex＋Zotero，平台服务于它们。
- 初始目录为 `D:\资料\毕设\文献`。
- 每天通常推荐 5–8 篇，兼顾当前课题和相邻方向；候选不足允许少推。
- 主要使用 DeepSeek API，可能补充千问或 Kimi；尽量在闲时批处理。
- 公开标题、摘要可以发送给配置的云端 API；全文和笔记默认留在本机。
- 当前没有时间做人工逐篇验证，需要可自动运行的质量门槛。

未确定但不阻碍规划：本机内存/显卡、每月金额上限、第二家 API 是否长期可用、期望日报时间、最终重点课题权重。正式实施先做小样本基准与调用量统计，再定资源和费用上限；本计划不假定已经获得这些参数。

## 3. 当前项目和语料的实际情况

### 3.1 已有能力与可复用资产

当前是 TypeScript/pnpm 工作区，Next.js/React 网页，Prisma/PostgreSQL 数据层，BullMQ/Redis 调度与队列。已有公开来源采集、保守去重、模型连接与主备路由、调用审计、确定性推荐、投递去重和 Vitest/Playwright 测试。

`apps/worker/src/manual-daily-run.ts` 已直接调用配置好的每日处理器，可作为一次执行后退出的基础。无需重写整条业务流水线。

尚未形成通用目录导入、Zotero 同步、本地全文解析、段落检索、embedding 或完整 RAG。现有多模型路由是故障回退，不能当作多模型交叉验证。当前引用结构校验也不等于原文支持核验。

几个需要优先处理的实际限制：

- 每日筛选先经过期刊白名单，可能漏掉无期刊信息的预印本及相关方向文献。
- 筛选 Prompt 只取摘要前 200 个字符，且沿用 10–15 篇与广泛物理方向目标。
- 兴趣主要是宽泛物理标签，未表达具体材料、器件机制和任务。
- Today 页面重新排序候选池，与每日真正选中、投递的集合存在口径差异。
- 缺少整次运行的持久化台账与可靠补跑。
- 普通论文按 30 天清理；本地用户资产必须与此隔离。
- 论文详情及部分操作依赖 DOI，不能完整支持无 DOI 的本地稿件。

### 3.2 指定目录适合做小规模试点

本次递归盘点得到 **36 个文件、20 个 PDF，整个目录约 76.3 MiB**；还包含 11 个 PNG、2 个 Markdown、DOCX、TeX 和配置文件。尚未逐篇解析 PDF、计算哈希或核实论文元数据，因此 20 个 PDF 不能直接等同于 20 篇独立论文。

已只读查看 `文献导读.md` 和 `每日阅读计划.md`。它们明确指向“二维光电感知与自主视觉”，并含 CFET 的阶段性阅读安排。建议首版研究画像：

- 主线：栅控/有符号光响应、二维/混维异质结、光晶体管、光电探测、类视网膜感知、感内计算与运动感知。
- 相邻方向：光谱计算、神经形态器件与系统、垂直集成/CFET。
- 背景方向：生物神经接口等按较低权重跟踪，不让它们因库内篇数较多而主导推荐。

这是依据现有导读提出的初始画像，不代表已确认最终课题，也不代表所有库内论文都已读过或都是正向偏好样本。

导读曾记录 26 个 PDF，并链接部分当前盘点中未出现的子目录。因此应重新建立清单、记录失效链接，不能把旧 Markdown 的数量、路径和事实直接作为当前索引。SI、旧调研报告、私人稿件应分别标记。

本次 Zotero 状态探测显示本地 API 设置已开启，但 API 和 connector 均超时；原因尚未定位。此次没有启动、重启或更改 Zotero。首版不以它始终在线为前提。

## 4. 轻量化的技术边界

### 4.1 保留什么，减少什么

| 保留 | 首版停止投入或移出默认路径 |
|---|---|
| TypeScript、pnpm 工作区、现有页面与共享包边界 | 公网部署、登录、多租户、云发布编排 |
| Prisma/PostgreSQL、来源事实与 AI 结果分层 | 首轮迁移 SQLite |
| 来源连接器、已有模型适配器和审计 | 为增加供应商数量而新增适配器 |
| 评分与投递去重，改为具体课题画像 | 大范围物理采集、期刊硬门槛、每日硬凑数量 |
| 一次性任务、可恢复的运行记录 | 默认常驻 worker 和 Redis/BullMQ 依赖 |
| 本地检索、原文定位、可重建索引 | 独立向量数据库、图数据库、GraphRAG、多 Agent 编排 |
| Markdown/JSON 日报，网页作为查看入口 | 邮件/聊天推送、复杂通知系统、重复的文献管理功能 |

保留 PostgreSQL 是控制改动量的选择，不是资源占用最小的选择。当前数据库有 PostgreSQL 原生类型、PrismaPg 适配和既有迁移/测试，换 SQLite 会扩大迁移面；以后只有实测资源负担明显时，再单独评估。

建议默认运行结构：

```text
Windows 任务计划程序 → 一次性 Node 任务 → 采集/筛选/索引/日报 → 退出
                                      ↕
                              本地 PostgreSQL
                                      ↕
                       按需启动的 Next.js 查看与检索入口

原始目录 / Zotero → 只读接入 → 本地解析与检索索引
公开标题/摘要    → DeepSeek + 可选第二模型
本地全文/笔记   → 本地检索；未来可接本地生成模型
```

Web 关闭不影响已配置好的每日任务。数据库在任务期间必须可用；若用 Docker，必须先处理 Docker Desktop/数据库启动与健康检查，不能暗示只安装任务计划就能自动运行。只绑定 loopback，不添加公网端口。

删除默认 Redis 依赖不能只停容器：需调整根 `dev`、配置中必填的 `REDIS_URL`、Web readiness 的强制 Redis 检查，以及 worker 启动路径。旧队列实现可以先保留为非默认模式，避免大面积删除代码。

### 4.2 Windows 上的“每日”如何兑现

建议起始排程为北京时间 07:00 左右，作为可调默认值，不是已配置的任务。电脑关机时不能生成日报；睡眠能否唤醒受系统和硬件设置影响，不作为首版承诺。

需要同时具备：任务计划禁止并行、错过后运行/登录补跑、程序单实例保护、数据库中稳定的日期与画像运行键、阶段状态和有界重试。崩溃后恢复同一运行，不能再投递另一份重复日报。不建设分布式租约系统。

采集根据上次成功水位加适量重叠窗口补漏，不能每天对整段 30 天候选重复付费筛选。区分发表时间、首次发现时间及来源更新时间，以免在线优先发表、迟到记录被漏掉。断网或来源失败不推进成功水位；部分来源可继续并标明覆盖不完整。

最终日报保存不可变的论文 ID 集合与推荐理由快照，作为 Today 的直接依据。快照发布与对应投递记录需在同一短事务内完成；模型调用在事务外执行。失败时保留上次成功日报，并显式显示“过期/本次部分失败”，不能显示为今日成功。

Microsoft 的 `StartWhenAvailable` 支持错过排程后运行，但它有适用条件与延迟，仍需程序级补跑和真实关机/恢复场景验收。[官方说明](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-startwhenavailable)

## 5. 本地文献库与 Zotero 的最小接入

先目录，后 Zotero 只读同步，不做首版双向同步。

1. 目录按允许的文件类型接入。第一批处理 PDF；Markdown 仅作为本地研究线索，TeX/DOCX/插图等暂不自动混入论文库。忽略隐藏配置、`.claude` 等目录，不跟随越出允许根目录的链接。
2. 建立资产清单：内部文献 ID、来源、路径映射、SHA-256、大小、文件角色、版本、解析状态、公开性与允许处理方式。内部路径不直接暴露为任意网页文件访问接口。
3. 相同哈希用于完全重复文件归组；DOI/arXiv 标识用于题录关联；相似标题只生成候选。预印本、正式版、SI 与报告保留角色，不静默合并为同一个文本。
4. 无 DOI 文献仍有内部 `paperId`。详情、检索、状态操作和证据定位逐步改用内部 ID，旧 DOI 链接保持兼容。
5. 原目录只读，不自动改名、移动、覆盖或删除。变更后重建对应派生索引；确认资产移除后使旧索引失效。根目录暂时不可访问不能解释为所有文件被删除。
6. 用户 PDF、笔记、Zotero 关联与长期索引不受普通候选的 30 天清理影响。临时候选、推荐历史和用户资产分开规定生命周期。
7. Zotero 可用后，通过本地 API 读取选定收藏夹、题录、条目键和必要附件关联。仅对选择的范围同步；保留服务器/库身份和版本水位。API 不可用时沿用上次状态和目录入口，不阻塞日报。

Zotero 官方提供本地 HTTP API，可读取本机数据库内容，无需直接操作其 SQLite 文件。对不同已安装版本先做能力探测；首版只读，不自动向 Zotero 新增、修改或删除条目。[本地 API 文档](https://www.zotero.org/support/dev/web_api/v3/local_api)

## 6. RAG：按隐私边界分成两个明确能力

### 6.1 本地全文检索与证据卡：首版必须可用

流程为：PDF 按页解析 → 保存页号与原文 → 按段落分块 → 本地关键词及多语 embedding 检索 → 返回证据卡 → 打开对应 PDF 页。

建议先用少量 PDF 验证 PDF.js 的 Node 解析与按页提取能力，再确定依赖版本；不先引入 Python 常驻服务或重型解析平台。PDF.js 官方提供 Node 示例，但论文的双栏、公式和表格质量仍必须对实际语料做试验。[官方示例](https://mozilla.github.io/pdf.js/examples/)

最小实现要求：

- 分块先试约 400–800 token、少量重叠，优先段落/章节边界；最终参数由语料基准决定。
- 每块保存资产版本、页号、原文、稳定哈希和可用定位。PDF 物理页号与印刷页码区分，首版可先做到“页号＋原文摘录”，精确高亮后置。
- 本地 CPU embedding 支持中文问题与英文论文，模型和版本固定；专业术语、材料缩写和中文别名由关键词检索补充。不能假定数据库自带高质量中文分词。
- 初期在 PostgreSQL 存派生文本和向量，应用内做有界精确相似度计算。先测延迟/内存；只有规模或实测性能需要时才引入 pgvector，不增加独立向量服务。pgvector 本身支持精确和近似检索，但这不意味着本项目首版必须安装它。[官方仓库](https://github.com/pgvector/pgvector)
- 识别空页、乱码、双栏顺序异常和低质量文本；无法可靠解析的文件显示“未纳入全文检索”。扫描 PDF、复杂表格、公式与图片理解后置，不伪装为已读懂。
- 文档内容仅作为数据，不允许其中的指令触发工具、联网或改变处理权限。

首版例子：“哪些论文讨论栅压改变正负光响应？”先返回相关原文、文件/论文、页号和出处。即使没有本地生成模型，也应完成这个闭环。

### 6.2 云端公开摘要 RAG：首版可做生成式问答

本地检索公开题录和摘要，将其中允许出站的记录交给 DeepSeek，生成带摘要引用的回答。界面明确写“依据公开摘要”，不能写“已综合你的全文库”，不能让云端模型引用它没有见过的本地段落。

问题中若含未公开课题细节，应留在本地模式。云端入口只处理用户明确在该模式输入的问题及公开内容，不自动拼入私人上下文。

### 6.3 全文生成式 RAG：条件满足后再做

**当前授权下，PDF 切块、全文摘要、笔记总结、由私人文本提取的画像以及全文 embedding，均不能因为体积变小就发送给云端。** 本地稿也不默认联网搜索或补元数据。

因此真正的跨论文全文生成问答，需要本地生成模型。在内存/硬件未知时，不承诺该能力的速度与效果。后续先试一款合适的量化模型，评估内存、延迟、中文专业回答与证据服从性；达不到要求就继续提供检索和证据卡，暂不做全文生成。

embedding 也必须在本机计算。首次下载模型文件可以在实施时作为明确的依赖安装步骤；运行时不上传语料。

从工程上把公开摘要索引与全文/私人索引分开。云端请求采用字段允许清单，不能靠 Prompt 中一句“不要泄露”守边界；云端评测和第二模型复核同样受这一限制。本地路径、文件名、资产哈希/标识和私人问题上下文不出站，日志、错误上报与推荐理由也不能旁路携带它们；需要的论文标识只使用明确公开的标识或请求内临时 ID。

## 7. 每日推荐：先缩小范围，再用模型

建议流程：

1. 研究画像由公开论文标题/摘要、明确主题词与用户配置建立；已有私人导读仅供本地使用，不能自动上传其内容或派生总结。先配置主线和相邻方向，不取所有 PDF 的单一平均向量。
2. 以现有 Crossref、OpenAlex、arXiv 连接器为基础，收窄到主题查询/类别/相关作者线索；首版启用最能提供合适题录和摘要的 1–2 个来源，其余作为补全或可选来源，不继续全物理领域遍历。
3. 先确定性去重，排除已投递论文，处理版本关系。期刊白名单变为软权重，不能硬拒无期刊预印本；完整可用摘要在有界 token 预算内进入模型，不再固定截前 200 字符。
4. 用公开种子相似度、关键词、主题、时效和多样性做便宜初筛。初始候选上限可试每天 40 篇主筛、15 篇二次复核，作为可调工作量上限，需用试跑数据修正。
5. 对入围摘要做 DeepSeek 判断与可选第二家模型独立判断，再生成最终名单。通常 4–6 篇主线、1–2 篇相邻，合计 5–8 篇；不足时如实报告，不重推凑数。
6. 每条包含“为什么与你有关、对应哪个公开种子或主题、摘要支持的内容、原文链接、预印本/正式版身份、分歧状态”。涉及个人全文的匹配关系只在本地计算和展示。
7. 日报同时保存 Markdown/JSON 和数据库快照；网页打开同一快照。已有论文回顾若以后加入，必须单列“回顾”，不能冒充当天新文献。

推荐只声称与主题相关，不根据摘要推断实验可复现、器件性能已独立核实或研究一定适合毕业课题。

## 8. 多模型：共识参与筛选，证据决定能否陈述

不建议把多个模型的自然语言答案直接取交集，或要求所有模型同意才保留候选。前者无法稳定定义“同一个结论”，后者会降低发现能力；不同供应商也可能共享错误模式。已有研究观察到显著的模型错误相关性，不能把一致率换算成事实正确率。[Correlated Errors in Large Language Models](https://arxiv.org/abs/2506.07962)

建议分层：

| 层次 | 方法 | 对结果的影响 |
|---|---|---|
| 确定性事实门槛 | 标识、来源、输入记录 ID、日期、引用 ID、摘录是否属于对应输入与版本 | 失败的记录/主张不能以已核对事实发布 |
| 双模型主题判断 | DeepSeek 与千问或 Kimi 独立看同一份公开摘要，不预先展示对方评分 | 共识优先；分歧保留并标记，不能直接等于事实错误 |
| 有限争议复核 | 仅对少量高价值分歧使用第三模型，建议每日最多 2–3 篇 | 形成额外意见；不能推翻缺证据的硬门槛 |
| 陈述支持检查 | 将结构化主张与其证据对应；区分摘录存在与语义支持 | 无依据的句子移除或降为不确定，严重不足时只展示题录/摘要 |

候选发现阶段保留有明确理由的模型并集；最终主荐优先采用双方认为相关且有证据的内容。争议候选可进入独立观察区，不为凑满主荐数量强行裁决。

每个模型返回固定字段：相关性等级、主题、证据摘录、建议、缺失信息与拒判原因。保留各自结果、实际模型标识、Prompt/输入版本和日期。超时、缺摘要、拒答是“没有结论”，不能计作赞成或反对。

只有一家 API 时仍可运行，但明确显示“单模型建议”；同一模型换 Prompt 或重试不能算第二个独立模型。第二家不可用或预算到限时，降级为单模型/题录日报并标注，不无限重试。

现有 30 篇 AI 初评与未完成的人工双评作为历史回归材料保留。取消“先完成人工双评才能开始一切开发”的前置依赖，改成分级试运行；不得把旧 AI 初评改名为人工通过或可靠性认证。

历史预检工具 `docs/evaluation-runs/tools/preflight-check.mjs` 也不能直接当生产门禁：现有摘录匹配较宽松，且告警不影响成功退出码。实施时建立明确的失败语义与负例测试，不把历史脚本成功退出解释成质量通过。

## 9. 没有人工验证时，怎样验收

可以自动验证工程正确性、来源一致性和模型行为的一部分；**不能自动证明所有科研结论正确，也不能知道遗漏了多少真正相关的新论文**。产品显示“自动检查通过/双模型一致”等具体状态，不显示“已验证正确率”。

自动测试应覆盖：

- 工程与隐私：云端请求只含允许字段；放入本地稿、笔记和私密标记后确认零外传；源 PDF 无修改；用户资产不被过期清理。
- 导入与检索：同哈希重复、同题不同版、SI、无 DOI、中文路径、文件移动、根目录离线、损坏 PDF、重建索引。
- 引用：每条引用存在且对应本次实际输入；摘录在对应页/摘要中可定位。存在不等于支持，因此另记录支持性模型意见；不能用宽松词重叠替代精确来源检查。
- 推荐：少候选、相邻方向、无摘要、晚到记录、多源重复、单模型失效、预算到限、来源部分失败。
- 运行：重复启动、进程中断、开机补跑、发表窗口跨日、日报发布失败；报告 ID 与投递 ID 一致。
- 问答：无答案、错误前提、张冠李戴、跨论文数值混淆、删掉关键证据、提示注入；无证据时拒答。

首批回归集可按论文划分开发集与保留集，从真实公开摘要或本地原文中构造可定位问题，并加入库外问题与故意破坏的引用。私人全文的测试用本地模板/本地模型生成，不发送给云端。模型自动生成的题目和答案是代理评测材料，不是真实金标准；不能反复调同一套题后宣称泛化提升。

建议初始门槛如下，属于实施目标，未在本轮测得：

| 检查 | 首轮验收目标 |
|---|---|
| 隐私、源文件保护、用户资产保留 | 固定回归场景零违规，否则阻止发布 |
| 引用身份/摘录来源有效性 | 输出中保留的引用 100% 可定位；失败时删除相关陈述或拒答 |
| 合成可回答题的证据检索 | 固定回归集 Recall@5 先争取 ≥85%，记录样本量与失败项 |
| 合成无答案题 | 固定回归集拒答率先争取 ≥90%，同时检查错误拒答；不得冒充真实用户准确率 |
| 本地检索性能 | 当前规模预热后 P95 争取 ≤2 秒，硬件实测后调整；生成时间另计 |
| 调度与幂等 | 故障/补跑测试无重复投递；连续 7 次有效运行有完整台账和明确降级状态 |

RAGAs 等自动评测可参考其“检索、忠实性、回答质量分开看”的思路，首版无需增加整套评测平台依赖；其中基于模型的指标仍是代理指标。[原论文](https://aclanthology.org/2024.eacl-demo.16/)

## 10. 调用成本与闲时运行

截至本次查阅，DeepSeek 官方定价页注明闲时费率为高峰的一半。其高峰为周一至周五 UTC 01:00–04:00、06:00–10:00（中国法定节假日除外），换算北京时间为 **09:00–12:00、14:00–18:00**，其余时间含周末与中国法定节假日为闲时。07:00 可作为初始批处理时间；实施时重新核对具体模型、时段和价格。[官方定价](https://api-docs.deepseek.com/quick_start/pricing/)

不在代码中固定历史模型名称、价格或节假日表，也不为闲时调度引入复杂的新服务。错过闲时后，可先生成题录/上次缓存日报，把可延后的模型工作排到下一窗口；不能把未经检查的名单显示成已复核结果。

费用控制的优先级：

1. 主题和来源收窄，减少无关候选。
2. 按论文版本、摘要哈希、研究画像版本、模型和 Prompt 缓存；相同输入不重复分析。
3. 只对入围摘要做第二模型检查，第三模型处理少量争议，不全量三重调用。
4. 限制输入、输出、候选数、重试数和并发；把推理 token 等实际计费项纳入统计。
5. 增加轻量的本地 token/费用台账、日/月预算和请求前预算预留；不能只在花完后显示金额。供应商金额不明时采用保守上限及调用量限制。

每月预算尚未确定，因此不提供未经试跑的月费用承诺。先做几次受限真实调用，按实际用量与当前官方单价计算“主筛＋二次复核＋输出＋有界重试”的费用，再确定日/月封顶。只实现成本控制，不引入商业计费系统。

现有 `apps/worker/src/jobs/ai-job.ts` 的幂等键未完整纳入内容版本，批量输入哈希主要依据论文 ID。实施时必须补摘要/文档版本、研究画像和验证策略版本，避免内容或兴趣改变后仍命中旧判断。

## 11. 分阶段实施计划

以下是有效开发工作日的粗估，按顺序做小批次变更，不是交付日期承诺。PDF 质量、现有测试环境和本地模型可能增加时间。

| 阶段 | 交付内容 | 依赖与验收 | 粗估 |
|---|---|---|---|
| P0：冻结范围与试验 | 更新定位、选择公开种子和主/相邻主题；盘点文件角色；取少量 PDF 做解析/CPU embedding 基准；查明 Zotero 可用性 | 明确出站允许清单、预算配置方案；不迁移原始目录 | 1–2 天 |
| P1：先让日报可靠 | 一次性任务正式入口、Redis 可选、课题定向采集、5–8 篇目标、运行台账/幂等/补跑、固定日报快照；首次真实调用前具备基本金额/请求/token/重试硬上限 | 在独立测试库验证失败恢复；可无第二 API 先运行并明确标注 | 3–5 天 |
| P2：接入本地全文 | 内部 paperId、资产生命周期隔离、目录增量导入、按页解析、关键词＋本地向量检索、证据卡；Zotero 只读接入可在本阶段后半段做 | 必须先保护用户资产；改文件/重建/缺文件不污染来源；有可用检索回归集 | 3–5 天 |
| P3：摘要 RAG 与自动质检 | 云端公开摘要回答、第二家模型独立主题判断、引用硬门槛、分歧/拒答、完善费用对账与预算展示；完善日报解释 | 不能把全文片段传云端；完整跑隐私/引用/故障回归，积累 7 次有效运行台账 | 3–4 天 |
| P4：可选全文生成 | 本地量化生成模型、小范围单篇问答，再评估跨论文 | 仅在硬件/延迟/质量基准过关后进行；否则停留在证据检索 | 另行估算 |

P0–P3 合计约 **10–16 个有效开发日**，按里程碑交付；不把全文生成、复杂 OCR、表格公式理解和双向 Zotero 同步算进首版。如果时间特别紧，先做 P0＋P1，日报可独立产生价值；第二步优先 P2，P3 的双模型部分逐步启用。

自动测试与隐私门槛应随各阶段建立，不能拖到 P3 才补。现有代码保留兼容，历史迁移不修改；增量 schema 变更先在专用测试库验证。正式数据迁移前备份并验证恢复，原始 PDF 无需迁移位置。
