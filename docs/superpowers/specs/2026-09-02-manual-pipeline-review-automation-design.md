# 手动全流程修改审查与每日自动化设计

## 目标

在独立 Git 分支上审查首次手动全流程运行形成的代码与文档修改，修复确认的问题，完成自动化测试、构建和本地网页关键路径验证；随后形成可供下一轮开发直接执行的每日全自动流程开发与部署规范，并仅在全部门禁满足后推送 GitHub。

## 范围

本轮覆盖以下改动链路：

- 公开来源采集后的期刊白名单过滤与批量 LLM 筛选；
- AI Provider、Prompt、Router、结构化输出与审计记录；
- `PaperScreening` 数据模型、迁移和数据库访问；
- 每日管线的筛选、选择、解读、Today 准备与过期清理；
- 单篇论文解读 API、Today 查询与推荐卡片交互；
- 手动运行报告、数据快照、语料元数据和可复现脚本；
- 后续每日全自动流程的开发、部署、观测、回滚和验收要求。

本轮不主动扩大到全文 PDF、RAG、公开互联网部署、用户认证、付费模型质量重跑或无关架构重构。

## 分支与版本控制

- 工作分支为 `codex/review-manual-pipeline-automation`，不直接修改或推送 `main`。
- 保留用户和其他智能体已有的全部工作区修改，不使用重置、强制覆盖或强制推送。
- `.worktrees/` 和 `.superpowers/` 是本地工具及工作树产物，加入 Git 忽略规则但不删除本地内容。
- `.env`、密钥、数据库备份、PDF、依赖、构建缓存和运行日志不得提交。
- `data/journal-corpus/` 中用于复现的说明、元数据与构建脚本可提交，但必须检查来源说明、文件体积和敏感信息。
- 提交按逻辑拆分：设计与计划、既有功能改动、审查修复与测试、自动化开发部署文档。每次提交只暂存对应文件。

## 审查设计

### 静态审查

逐文件检查类型契约、输入验证、错误处理、状态迁移和边界条件，重点关注：

- 筛选输入是否仅包含允许发送的公开元数据；
- Provider 与 Router 的主备回退、错误映射和 usage 记录是否一致；
- 批次失败是否隔离，部分成功是否被真实记录；
- 数据库唯一约束、迁移顺序、幂等写入和查询上限是否合理；
- 每日时间窗口与 `Asia/Shanghai` 时区是否一致；
- 重复调度、并发单篇解读和重试是否会产生重复调用或状态覆盖；
- Today 排序、昨日统计、候选池和有无解读标记是否符合页面语义；
- API 是否稳定返回业务错误，并避免向客户端泄露内部异常或秘密；
- 客户端按钮在加载、成功、失败和重复点击时是否行为明确。

发现问题时只做与本轮目标直接相关的最小修复。行为变化必须增加或更新回归测试；修复前先运行目标测试复现失败，修复后重新运行目标测试。

### 自动验证

验证按从快到慢的顺序执行：

1. 新增模块和受影响模块的定向 Vitest；
2. Prisma Client 生成与迁移结构检查；
3. `pnpm lint`；
4. `pnpm typecheck`；
5. `pnpm test`；
6. `pnpm build`；
7. `pnpm test:e2e`，使用测试专用数据库和 Mock Provider，不触发真实模型或公开来源网络请求。

任何失败都必须保留命令、退出码和关键错误信息，并先定位根因再修改。不得用跳过测试、跳过钩子或降低断言来换取通过。

## 网页试运行设计

使用本地依赖和应用完成可见交互验证：

- 存活与就绪端点返回预期状态；
- Today 首页能加载，统计、排序和推荐卡片内容正确；
- 已解读论文可进入详情页并显示来源边界；
- 未解读论文显示单篇 AI 解读入口，按钮状态和错误反馈可用；
- 收藏、阅读状态与个人库关键路径没有回归；
- 模型设置页可打开且不会把已保存 API Key 返回浏览器；
- 桌面和窄屏关键布局无明显静态资源或交互异常。

网页试运行默认使用 Mock Provider 或已有测试夹具。真实 Kimi 调用不属于本轮自动验证；只有用户另行明确授权且本地密钥已通过安全方式配置时才可执行。

## 每日全自动流程文档设计

新增详细开发与部署规范，至少包括：

- 当前手动流程与目标自动流程的阶段映射；
- 调度时间、时区、窗口计算、幂等键和分布式运行锁；
- `PENDING`、`RUNNING`、`SUCCEEDED`、`PARTIAL`、`FAILED` 状态及转换条件；
- 采集、白名单过滤、LLM 筛选、解读、Today 准备和清理的输入输出契约；
- 限流、超时、结构化输出失败、指数退避、最大尝试次数和死信处理；
- 运行指标、结构化日志、健康检查、告警条件与人工处置手册；
- 环境变量清单、秘密注入、数据库迁移、Redis/PostgreSQL 依赖和最小权限；
- 本地、受保护单机和未来容器化部署边界；
- 备份、恢复、发布、回滚、停机与数据一致性检查；
- 开发任务拆分、测试矩阵、连续手动验收和启用自动调度的上线门禁。

文档必须区分“当前已实现”“本轮建议实现”“未来可选增强”，不得把规划中的运行锁、告警或状态追踪描述成已有能力。

## 推送门禁

只有同时满足以下条件才推送远端分支：

- 提交清单不含秘密、本地工具目录、构建产物或无来源的大文件；
- 受影响测试、完整测试、类型检查、Lint 和构建均有本轮新鲜通过证据；
- 网页关键路径已实际打开并验证，结果记录在交付说明中；
- 代码审查发现的高优先级问题已修复，或明确列为阻断项并停止推送；
- 自动化开发与部署文档完成并通过一致性检查；
- `git diff --check`、最终 `git status` 和待推送提交范围均已复核。

推送目标为 `origin/codex/review-manual-pipeline-automation`，不创建或更新 `main`，不使用 force push。

## 成功标准

本轮成功意味着：用户能够在 GitHub 独立分支上审阅一组边界清晰、可回溯的提交；代码和网页关键路径均有可复查的验证证据；自动化文档能够让下一次开发直接按阶段、测试和部署门禁推进，而不需要重新推断首次手动运行的隐含流程。
