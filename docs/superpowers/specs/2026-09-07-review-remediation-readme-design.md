# 项目审查修复与 README 重构设计

## 目标

在不扩大产品功能范围的前提下，修复本轮审查确认的每日投递与去重缺陷，整理 30 篇质量评审材料，恢复可审查的 Git 分支状态，并把根 README 重构为中文主文档加英文精简版。全部改动在独立审查分支完成，验证通过后由用户确认是否推送。

## 已选方案

README 采用方案 A：中文主文档承担完整介绍、启动、架构、安全边界、验证和路线图；英文部分只保留定位、核心能力、快速启动、安全边界和文档入口。两部分共享同一组事实，不再逐段镜像，以降低重复内容过期的概率。

## 范围

### 包含

- 将本地未出生分支安全连接到远端 `origin/codex/review-manual-pipeline-automation`，保留全部工作区内容。
- 修正 `DAILY_DELIVERY_RECENCY_DAYS=0` 的配置契约，使文档、类型和运行时一致。
- 把“已投递”从候选选择阶段移到 Today 成功准备之后，失败时不抑制未发布论文。
- 将重复抑制改为论文级判断：论文只要存在近期成功投递记录，就不能因新增 screening 记录而重新入选。
- 为上述行为增加配置、仓储和每日管线回归测试。
- 统一 30 篇评审表、初评汇总和快照说明，明确哪些是输入快照、哪些是最终评审结果。
- 将本地代理记忆和一次性脚本排除在提交范围外；可复现评审脚本只有在用途、输入、输出和安全边界清晰时才纳入版本控制。
- 重写根 `README.md`，准确描述当前能力、限制、开发状态和下一步路线。

### 不包含

- 不在本轮实现 `DailyPipelineRun`、分布式租约、告警、生产部署或完整发布流水线。
- 不新增 PDF 全文处理、Zotero 同步、向量数据库、RAG 或用户认证。
- 不重新调用真实模型，不重跑需要付费的论文解读。
- 不选择或新增开源许可证；许可证类型需要用户单独决定。
- 不直接修改或推送远端 `main`，不使用强制推送。

## 投递与去重语义

每日管线先读取候选、执行确定性选择和逐篇解读，再准备 Today 数据。只有 Today 准备成功后，才把本轮实际选择的论文标记为已投递。解读允许出现部分失败，因为 Today 可以如实展示缺少解读的论文；但如果 Today 准备整体失败，本轮任何论文都不能获得新的投递时间。

候选查询以论文为去重边界。论文必须至少有一条 `selected=true` 的 screening，同时不能存在 `deliveredAt >= cutoff` 的 screening。用于排序的 screening 也必须来自满足当前选择条件的记录，避免父查询与嵌套选择使用不同过滤条件。

当前改动仍不承诺多进程原子抢占。自动调度继续默认关闭，部署文档继续要求在实现运行账本和租约之前只运行一个 worker。并发安全作为后续独立阶段处理。

## 配置契约

- `DAILY_INGEST_WINDOW_DAYS`：1–365 的整数，默认 30。
- `DAILY_DELIVERY_RECENCY_DAYS`：0–365 的整数，默认等于采集窗口。
- 值为 0 时关闭重复投递抑制，并跳过 `deliveredAt` 写入。
- 非整数、负数或超过上限时启动失败，并返回包含变量名的稳定错误。

## 评审材料整理

30 篇评分表的头部状态必须与现有内容一致，不再声称 AI 输出“待产出”。初评汇总的数量必须由逐篇记录重新计算，保证各档数量合计为 30。11 篇 `output-snapshot` 标为早期输入快照，不能描述为完整 30 篇结果；315 KB 的 Today 响应只有在能说明复现用途且不包含私密用户状态时才提交，否则保留本地并加入忽略规则。

一次性文件 `.tmp-edit-config.mjs`、`fetch-test.mjs` 和 `.workbuddy/` 不进入提交。`docs/evaluation-runs/scripts/` 中的脚本若纳入提交，必须只读取显式环境变量、拒绝非 loopback 数据库、输出到固定评审目录，并在评审指南中给出运行方式。

## README 信息架构

中文主文档按以下顺序组织：

1. 一句话定位与项目状态；
2. 为什么做、适合谁；
3. 当前已实现能力；
4. 系统架构和数据边界；
5. 五分钟本地启动；
6. 模型连接与真实调用提醒；
7. 测试和验证；
8. 已知限制；
9. 路线图和文档入口；
10. 英文精简版。

README 不展示不存在的 CI、覆盖率或发布徽章，不声称尚未实现的运行锁、完整 RAG 或生产部署已经可用。安装命令必须与根 `package.json`、`.env.example` 和运维文档一致。项目没有许可证时只陈述事实，不默认宣称 MIT 或允许再分发。

## 错误处理

- 投递标记失败必须让每日任务失败或返回明确的部分失败状态，不能静默吞掉。
- Today 准备失败时不得写入投递时间。
- 配置错误在启动阶段失败，不进入数据库或模型调用。
- 评审脚本缺少数据库变量或检测到非 loopback 主机时立即停止。
- Git 修复前后比较远端基线差异清单，任何工作文件减少都视为失败并停止后续操作。

## 测试与验收

- 配置测试覆盖 0、负数、小数、上限和默认继承。
- 仓储单元测试覆盖“存在近期投递记录时整篇排除”和“只读取符合条件的 screening”。
- 每日管线测试覆盖 Today 成功后写入、Today 失败不写入、写入失败可观察。
- Prisma 迁移在新的 loopback 测试 schema 应用成功。
- 完整 Vitest、Lint、类型检查、生产构建和桌面/移动 Playwright 全部通过。
- `git diff --check` 无错误；拟提交文件不含 `.env`、本地代理状态、临时脚本、PDF、备份或构建产物。
- README 中所有相对链接存在，启动命令与脚本名称一致。

## 提交边界

建议形成三个可独立审查的提交：

1. `fix(pipeline): make daily delivery dedupe truthful`
2. `docs(evaluation): reconcile manual review evidence`
3. `docs(readme): clarify project status and local setup`

在三个提交和完整验证证据准备好之后停止，不执行 `git push`，等待用户最终确认。
